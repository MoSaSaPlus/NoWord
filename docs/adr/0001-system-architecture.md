# ADR-001：NoWord 系统架构与技术栈

## 状态

提议中。该 ADR 随对应 Pull Request 合并后视为接受。

## 日期

2026-07-20

## 背景

NoWord 是一个单用户慈善捐款追踪 Web 应用。MVP 需要支持身份认证、交易管理、回收站、统计图表、PDF 报告、审计和线上部署。

项目同时承担学习目标：开发者需要亲自完成应用代码，并通过项目练习前端、HTTP API、数据库、测试、Git 和部署。架构应具备清晰边界和企业项目的基本质量保障，但不能为了模拟大型系统而引入与当前规模不匹配的复杂度。

本决策受以下约束影响：

- 交易属于敏感数据，不能存储在浏览器 `localStorage` 中。
- 金额必须以人民币“分”的整数形式保存和计算，不能依赖浮点数或专门的金额库。
- Dashboard 需要进行按月、按年和同比聚合查询。
- 系统需要支持服务端分页、筛选和排序。
- 身份认证采用服务端 Session，不在浏览器持久化 JWT。
- 产品以 Web 应用形式部署到 `mosasanb.com`，前端与 API 优先保持同源。
- MVP 只有一个账户，但数据模型不得依赖匿名用户或固定的全局用户状态。

## 决策

### 1. 总体架构

NoWord 采用前后端分离的模块化单体架构，并保存在同一个 Git 仓库中。

```text
Browser
  |
  | HTTPS
  v
Web Application
  |
  | /api/v1/*
  v
Fastify API
  |-- Authentication
  |-- Transactions
  |-- Dashboard
  |-- Reports
  |-- Audit
  `-- Health
  |
  v
PostgreSQL
```

前端和后端在代码结构及运行时上保持独立，通过 REST API 通信；生产环境通过同一域名对外提供服务。后端业务模块部署为一个进程，不拆分微服务。

### 2. 仓库与包管理

- 使用 pnpm 管理依赖。
- 使用 pnpm workspace 组织单仓库。
- 提交 `pnpm-lock.yaml`，确保本地、CI 和生产环境使用一致的依赖版本。
- 应用代码和共享契约按以下方向组织：

```text
apps/
  web/          React Web 应用
  api/          Fastify API 应用
packages/
  contracts/    API 数据结构和校验规则
docs/           需求、ADR 和其他设计文档
```

只有确实被多个应用共同使用的内容才能进入 `packages`，避免把它变成缺乏边界的公共工具目录。

### 3. 前端

- 使用 React 和 TypeScript。
- 使用 Vite 负责本地开发和生产构建。
- 使用 React Router 管理 Dashboard、Transactions、Recycle Bin 和 About 等页面路由。
- 使用原生 `fetch` 或对其进行轻量封装访问 REST API；引入服务端状态管理库必须由实际复杂度证明必要性。
- 使用 CSS Modules 和 CSS Variables 实现样式、主题变量及组件作用域隔离。
- 使用 Recharts 展示 Dashboard 图表。
- 组件按业务功能组织，不按 `components`、`hooks` 等技术类型堆积全部文件。

建议的前端模块边界：

```text
src/
  app/           应用入口、路由和全局布局
  features/      auth、transactions、dashboard、reports
  shared/        通用 UI、API 客户端和无业务含义的工具
```

### 4. 后端

- 使用 Node.js 和 TypeScript。
- 使用 Fastify 作为 HTTP 服务框架。
- 使用 REST + JSON 提供业务 API，MVP API 前缀为 `/api/v1`。
- 使用 Zod 定义和执行运行时输入校验；前端校验只用于改善体验，服务端必须独立校验所有输入。
- 使用 Fastify 内置的 Pino 日志能力输出结构化日志。
- 业务代码按模块组织，每个模块内部区分 HTTP 路由、业务服务、数据访问和输入输出结构。

建议的后端模块边界：

```text
src/
  app/           应用组装和基础插件
  modules/
    auth/
    transactions/
    dashboard/
    reports/
    audit/
    health/
  shared/        配置、数据库连接和跨模块基础设施
```

HTTP 路由只处理协议相关工作，业务规则放在服务层，数据库访问集中在数据访问层。业务服务不得直接依赖 HTTP 请求或响应对象。

### 5. 数据库与数据访问

- 使用 PostgreSQL 作为生产和本地开发数据库。
- 使用 Drizzle ORM 管理数据库结构、迁移和类型安全的数据访问。
- 数据库迁移必须提交到版本库，禁止依赖运行时自动同步结构。
- Dashboard 等聚合场景允许使用明确、可测试的 SQL，不要求所有查询都通过 ORM 的高级封装完成。
- 本地开发使用 Docker Compose 启动 PostgreSQL，Node.js 应用可以直接在宿主机运行。

关键数据规则：

- 金额在数据库中保存为整数分，业务运算只使用整数。
- API 接收用户输入的十进制金额字符串，由后端校验并转换为整数分。
- 捐款日期使用 PostgreSQL `DATE`，API 使用 `YYYY-MM-DD` 字符串。
- 业务表包含用户标识，即使 MVP 只有一个账户，也必须按当前用户限制查询。
- 删除交易采用软删除；到期清理由受控任务执行。
- 创建、修改、删除、恢复和导出等关键操作写入独立审计记录。

### 6. 身份认证与会话

- 唯一账户由部署管理员通过受控初始化流程创建，不建设公开注册入口或管理员后台。
- 密码使用成熟安全库提供的 Argon2id 实现进行哈希。
- 登录成功后创建随机、不可预测的服务端 Session。
- Session 数据保存在 PostgreSQL，浏览器只保存 Session Cookie。
- Cookie 必须使用 `HttpOnly`、`Secure` 和适当的 `SameSite` 策略。
- 退出、密码变更和管理操作可以使已有 Session 失效。
- 登录接口需要限流，并记录成功及失败的审计事件，但不得在日志中记录密码。

### 7. API 约定

- API 使用 `/api/v1` 前缀，为将来的不兼容变更保留升级空间。
- 输入和输出使用 JSON；PDF 下载除外。
- 列表接口在服务端完成分页、筛选和排序。
- 可排序字段必须使用后端允许列表，不能直接将客户端字段拼接进 SQL。
- 错误响应至少包含稳定错误代码、用户可理解的信息和请求标识。
- 字段校验失败时返回字段级错误集合，支持前端一次展示全部输入问题。
- API 契约在后续 API 设计任务中详细定义，并生成或维护 OpenAPI 文档。

### 8. PDF 报告

- PDF 在服务端生成，浏览器不直接接触数据库或完整数据集。
- 服务端按照当前用户和报告日期范围查询有效交易，再渲染受控 HTML 模板并转换为 PDF。
- 优先评估使用 Playwright 的 Chromium 生成 PDF，以复用端到端测试所需的浏览器运行时。
- 在确定部署平台后，必须验证浏览器运行时、字体和内存限制；若平台不适合运行 Chromium，再单独记录替代方案。

### 9. 测试策略

- 使用 Vitest 编写前后端单元测试。
- 使用 React Testing Library 测试前端组件的用户行为。
- 使用 Fastify `inject` 测试 API 路由，不为常规 API 测试启动真实网络端口。
- 数据库查询和迁移使用独立测试数据库执行集成测试。
- 使用 Playwright 执行登录、交易增删改查、回收站、Dashboard 和 PDF 等关键端到端流程。
- 金额边界、日期边界、同比除零、权限隔离和软删除必须具有自动化测试。

### 10. CI 与部署

- 使用 GitHub Actions 执行依赖安装、格式检查、静态检查、类型检查、测试和构建。
- `main` 分支只接收通过 Pull Request 和 CI 的变更。
- 生产环境由同一个域名提供 Web 页面和 `/api`，避免不必要的跨域会话配置。
- 数据库使用托管 PostgreSQL，并按照需求文档执行自动备份、异地备份和恢复演练。
- 具体云服务商、服务器地域和部署编排方式在部署任务开始前另行记录。

## 质量边界

MVP 必须具备：

- TypeScript 严格模式。
- 可重复执行的数据库迁移。
- 服务端输入校验和身份授权。
- 自动化测试及 CI。
- 结构化日志、请求标识和审计记录。
- 环境变量校验和安全的秘密管理。
- 可执行的生产备份及恢复流程。

MVP 不要求：

- 微服务、消息队列或事件总线。
- Kubernetes。
- Redis；除非后续需求证明 PostgreSQL Session 无法满足要求。
- GraphQL。
- 多区域容灾和自动水平扩容。
- 通用组件库或复杂设计系统。

## 备选方案与取舍

### Next.js 全栈

未选择作为 MVP 主架构。它可以减少部署单元，但会弱化前端、HTTP API 和后端边界的学习目标。若未来需要服务端渲染或公开页面 SEO，可以重新评估。

### NestJS

未选择作为 MVP 后端框架。NestJS 提供完整的依赖注入和模块体系，但当前项目规模不需要其额外抽象。Fastify 更便于开发者直接理解 HTTP 生命周期和模块组装。

### 微服务

未选择。当前业务规模、团队规模和部署目标都不能证明拆分服务所增加的网络、部署、观测和数据一致性成本是合理的。

### MongoDB

未选择。交易、用户、审计和统计之间具有明确关系，PostgreSQL 更适合一致性约束、聚合查询和财务类数据。

### 浏览器本地持久化

未选择。交易属于敏感数据，浏览器存储不能满足身份隔离、可靠备份和线上访问要求。

### 持久化 JWT

未选择。单一同源 Web 应用不需要无状态令牌带来的复杂度，服务端 Session 更容易撤销并控制有效期。

## 影响

积极影响：

- 前后端边界清晰，可以系统练习完整 Web 开发流程。
- 单仓库和统一 TypeScript 降低个人项目的上下文切换成本。
- PostgreSQL 能同时支持交易一致性、筛选和 Dashboard 聚合。
- 模块化单体便于测试、部署和后续演进。
- 同源部署简化 Cookie、HTTPS 和跨域安全配置。

成本与限制：

- 前后端分离需要维护 API 契约和两套构建流程。
- PostgreSQL Session 会增加数据库读写，但对单用户 MVP 可以接受。
- 服务端 PDF 生成会增加部署镜像大小和运行内存。
- Drizzle 不能替代 SQL 基础知识，开发者仍需理解迁移、索引和查询计划。
- 模块边界需要持续审查，否则单体内部仍可能产生过度耦合。

## 实施顺序

1. 初始化 pnpm workspace、Web 应用和 API 应用。
2. 建立格式检查、类型检查、测试、构建和 CI。
3. 实现健康检查，验证前端、API 和运行环境链路。
4. 建立 PostgreSQL、Drizzle 和迁移流程。
5. 实现账户初始化、登录、Session 和受保护页面。
6. 实现交易新增、列表、筛选、排序和分页。
7. 实现修改、软删除、回收站、恢复和到期清理。
8. 实现 Dashboard 聚合查询和图表。
9. 实现 PDF 报告和审计查询。
10. 完成安全、性能、备份恢复和生产部署验证。

## 后续需要单独确定的事项

- Node.js、pnpm 和 PostgreSQL 的具体受支持版本。
- Session 有效期、续期和并发会话规则。
- 数据库表、索引和约束的具体设计。
- REST API 的详细资源路径和错误代码。
- 具体云服务商、部署方式和备份存储服务。
- PDF 字体、模板和浏览器运行时部署方案。

当系统扩展为多用户产品、支持多币种、出现独立团队或需要分别扩容模块时，应重新评审本 ADR。
